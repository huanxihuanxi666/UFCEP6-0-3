# 明日展示：五人讲述与追问提示

PPT 只展示两类内容：真实的 operational BPMN 和 measurable acceptance criteria。每位成员讲自己的流程图，再用相邻表格说清楚如何判定通过。表格写的是**验收条件**，不能把尚未执行的路径说成已经通过。流程图来自当前 BPMN；细节较密时，可在放映中放大相应区域。

## 开场：全组主流程（第 1–2 页）

建议第一位讲者用 45–60 秒说明：转诊决定是否进入预约；预约后进入资金清算；清算通过才进入治疗；治疗子流程结束后进入诊所信件。主流程调用五个子流程。以 M1–M4 说明我们检查的是**子流程是否被调用、调用次数、完成顺序与 incident 数**，不是只看模型画得是否完整。

- **为什么资金清算在治疗前？** 常规路径要求先确认资金来源；但临床评估目前在治疗子流程内，顺序仍需业务复核。紧急治疗有单独 override 路径，不能把它说成一般规则。
- **怎样运行完整路径？** 部署同一版本的主流程及五个被调用流程，启动主实例，按顺序完成表单任务并运行外部 worker，最后核对主实例、五个子实例和 incident。单独启动子流程只适合局部测试，不能证明完整主流程。
- **有哪些主要终止路径？** 转诊未接受、资金未清算、完整路径结束；咨询和退款还可由独立消息入口启动。各路径的实例记录要分别保存。

## DENG JIN WANG：转诊（第 3–4 页）

讲述主线：转诊录入 → 检查资料 → 顾问审核 → ACCEPT / REJECT / MORE_INFORMATION / REDIRECT。缺资料回去补，只有 ACCEPT 向预约交接。表单的患者 ID、转诊 ID、转诊机构是必填；顾问决定和理由也是必填。

- **为什么设计四个结果？** 接受、拒绝、要求更多临床资料、转向其他服务是四种不同业务结局。用 R3 分别启动四个实例，看是否抵达对应任务或结束事件。
- **MORE_INFORMATION 与资料不全有何区别？** 前者是顾问审阅后的临床信息请求；后者是在顾问审阅前补齐支持资料。R2 要证明补资料前顾问任务出现 0 次。
- **是否真的和转诊机构自动通信？** 图上的消息流表示业务协作；目前没有对应自动发送 worker，不能声称已经完成外部系统集成。

## WU JIA WEI：预约（第 5–6 页）

讲述主线：提交预约需求 → worker 搜索时段 → 无号源则修改后重搜；有号源则确认并发信；两周内预约额外电话联系。电话结果为 ANSWERED、NO_ANSWER、WRONG_NUMBER、RESCHEDULE；只有 RESCHEDULE 回到搜索。

- **两周如何计算？** worker 按执行当天计算 0–14 天，包含第 14 天；第 15 天不走电话路径。A3 用“今天 +14/+15 天”做边界测试。
- **无号源如何处理？** 进入可修改请求的人工任务，再次调用搜索；A2 检查确实发生第二次搜索，且首次没有交接。
- **没有接通还会交接吗？** 当前模型中 NO_ANSWER 和 WRONG_NUMBER 记录结果后也可交接。这是当前逻辑，不要说成已经联系成功；若业务规则要求必须接通，需要改模型。

## LIN JIA QIANG：治疗（第 7–8 页）

讲述主线：临床评估与同意 → 治疗请求授权 → 资源检查 → 给药及周期复核。不同意不调用资源检查；未授权返回更正；资源不足修改请求后重试；更多周期按 CONTINUE / DELAY / MODIFY 分流。

- **不同意治疗会怎样？** 治疗子流程结束，但主流程仍启动信件子流程。T1 同时核对资源检查 0 次、给药 0 次、信件 1 次。
- **周期数会自动执行几次吗？** 表单记录 numberOfCycles 和 cycleFrequency，但当前模型通过 `moreCycles` 人工决定是否继续，没有自动计数器。不能把填写的数字当作引擎已执行次数。
- **MODIFY 触发财务重审吗？** `financialImpact=true` 进入人工确认更新清算任务；不是自动重新审批。T4 用三种临床决定分别验路径。

## WU TONG YU：资金、付款与退款（第 9–10 页）

讲述主线：资金来源有 HOSPITAL、EXEMPTION、INSURER、PATIENT 四类；保险需要批准；患者付款按成功、失败重试、待调查分流。退款独立启动，只有“需要退款且批准退款”才调用退款 worker。

- **支付失败和支付状态不明有何区别？** DECLINED 可进入编辑后重试；CONFIRMATION_LOST / DUPLICATE_RISK 先调查，当前流程不会自动发起第二次支付。F2、F3 用 worker 调用次数检查。
- **是否保证绝不重复扣款？** 没有持久化幂等键，不能保证支付平台层面的去重。当前只做到风险结果分流和调查前不自动再发起请求。
- **退款何时执行？** `refundRequired=true` 且 `refundApproved=true` 同时成立。F4 用四种布尔组合验证，只有 1/4 会调用退款 worker；服务本身仍是模拟。

## XIAO YU YING：咨询与诊所信件（第 11–12 页）

讲述两个入口：患者咨询按 ADMINISTRATIVE / FINANCIAL / CLINICAL 分派，紧急临床问题额外升级；主流程的信件先准备、获批准、核对收件人，再发送。延迟监控经过 P7D 定时器，之后人工给出 7D_TO_1M / OVER_1M / OVER_3M 年龄段来决定提醒或升级。

- **批准拒绝后能修改正文吗？** 当前流程不会自动返回一个明确的可编辑正文任务；这是仍需完善的路径，不要把 L2 的再次批准当作完整修订闭环。
- **七天目标自动保证了吗？** 没有。P7D 从该定时器进入时开始计时，未从咨询日期自动起算；年龄段也是人工选择。L4 是待实现/待实测的目标：发送时间不晚于咨询时间 +7 天。
- **怎样验延误升级？** L3 对三个年龄段分别走实例，检查相应提醒或升级任务；真实计时要等待 P7D 或使用可审计测试时钟，不能仅手动改变量就声称定时器通过。

## 全组统一回答口径

1. **什么叫 measurable？** 给定明确输入后，统计任务或 worker 调用次数、检查变量及结束路径，结果能判定通过/失败。例如“14 天到电话，15 天不到电话”。
2. **表格是不是测试结果？** 不是。它们是可执行的验收标准；尚未提供当前完整部署的逐路径运行记录，不能把 4/4 或 3/3 读成已通过数量。
3. **如何证明运行？** 保存流程版本、主/子实例 ID、表单输入、变量历史、任务和 worker 记录、结束状态及 incident；按每行标准逐例核验。
4. **最需要改进什么？** 咨询日起算的七天信件时限、信件拒批后的可编辑返工、支付幂等保护，以及资金清算与临床评估的业务顺序。这些都是模型与真实业务之间尚需验证或补强的点。
